# 기능을 추가하거나 바꿀 때 점검할 것

VPyLab에 새 기능을 넣거나 기존 동작을 바꿀 때 함께 고치고 확인해야 하는 곳을 모았습니다. 2026-11-19~20의 빛·소리 작업에서 실제로 빠졌거나 문제가 된 것을 바탕으로 썼습니다. 해당하는 절만 보면 됩니다.

먼저 `docs/SCOPE.md`(범위와 기능 동결)와 `AGENTS.md`(표준 Python·VPython을 따른다는 원칙)를 읽습니다.

## 1. 학생이 쓰는 이름이나 값을 새로 만들 때

함수, 인자, 속성, `textures.xxx`, `type='xxx'` 같은 값을 추가하는 경우입니다. 한 곳만 고치면 "되기는 하는데 학생은 모르는" 기능이 됩니다.

| 고칠 곳 | 무엇을 | 어긋나면 |
|---|---|---|
| `client/src/engine/vpython-api.py` | 실제 동작 | — |
| `client/src/data/docs.js` | 설명, 인자 표, 실행되는 예제(한국어·영어) | 자동 완성에 뜻이 안 나옴. 문서 예제는 테스트가 실제로 실행합니다. |
| `client/src/components/editor/python-completions.js` | 점 뒤 목록(`members`), 내장 이름의 뜻(`extras`) | 편집기에서 이름이 추천되지 않음 |
| `client/src/data/code-vocabulary.js` | 낱말 카드(뜻, 읽는 법, 설명, 예시, 영어) | 코드 아래 "단어 뜻"에 안 나옴 |
| `client/src/i18n/catalogs/en-ui-text.json` | 화면에 보이는 한국어 문구의 영어 | 영어 화면에 한국어가 섞임. CI의 번역 키 검증이 잡습니다. |
| `server/utils/standalone-template.js` | 내려받은 HTML의 파이썬 API와 렌더러 | 편집기에서는 되는데 내려받은 HTML·갤러리에서 안 됨 |

규칙

- **재질(`textures.`)**: `docs.js`의 `textures-presets` 표에 넣으면 자동 완성에 나옵니다. 엔진의 `_TexturePresets`와 어긋나면 `python-completions.test.js`가 실패합니다.
- **낱말 카드**: 흔한 변수 이름과 겹치는 낱말(`volume`, `points`, `menu`, `camera`)은 `wordContexts`에 "그 뜻으로 쓰인 자리"의 정규식을 함께 넣습니다. `sun`, `moon`, `earth`처럼 변수 이름으로 더 자주 쓰는 낱말은 카드로 만들지 않습니다.
- **문자열 값**(`type='felt'` 등)은 문자열 안이라 자동 완성과 낱말 카드가 닿지 않습니다. 문서의 인자 설명에 값과 한글 이름을 적습니다.
- 예제·미션·튜토리얼·복사·다운로드에 제공하는 코드는 같은 학생 코드 원칙(AGENTS.md)을 따릅니다. 묶은 도형도 `pos`, `color`, `visible`로 직접 조작하는지 확인합니다.
- **표준 VPython과 다른 동작**을 넣을 때는 확장임을 문서에 적고, 기존 코드의 뜻이 바뀌지 않는지 확인합니다. 예: 값의 범위를 자동으로 바꿔 해석하는 규칙은 `color.white * 2`처럼 이미 쓰이는 표현의 결과를 바꿀 수 있습니다.

## 2. 그리기(렌더러)를 바꿀 때

`vpython-bridge.js`, `Viewport3D.jsx`, `texture-system.js` 등입니다.

- **기존 작품이 달라 보이지 않는가.** 새 효과는 새 이름에만 적용합니다. 기존 재질·기본 조명·기본 분할 수를 바꾸면 이미 만든 작품이 전부 달라집니다.
- **느리게 도는 정상 프로그램을 느린 기기로 오해하지 않는가.** 화면은 바뀔 때만 그립니다(`render-gate.js`). 그린 프레임 사이의 간격은 `rate(20)`이면 원래 50ms입니다.
- **만든 것을 해제하는가.** geometry, material, texture, 캔버스. 여러 물체가 함께 쓰는 텍스처를 한 물체가 해제하지 않는지도 봅니다.
- **비동기로 받는 자산**: 받는 동안의 임시 모습, 실패했을 때의 모습, 받는 중에 정지·재실행했을 때를 각각 확인합니다. `scene.waitfor('textures')`가 끝까지 기다리는지도 봅니다.
- **셰이더를 고칠 때**: 휴대폰·태블릿에서 컴파일되는지 실제 기기에서 확인합니다.
- **녹화와 썸네일**은 같은 캔버스를 씁니다. 캔버스 크기나 해상도를 실행 중에 바꾸면 둘 다 영향을 받습니다.
- **내려받은 HTML**에도 같은 명령 처리가 따로 있습니다(1절의 표).

## 3. 소리를 바꿀 때

`sound-system.js`와 그 주변입니다.

- **정지**: 정지 버튼, 화면 이동, 오류, 재실행에서 소리가 남지 않는가. `stopAllSounds()`가 새로 만든 노드·타이머·버스까지 정리하는가.
- **발음 한도(24개)**: 한 음이 소스를 여러 개 쓰는 악기는 한도를 빨리 채웁니다. 한도에서 새 음을 버리지 않는지, 한꺼번에 몰린 요청에 노드 수가 늘지 않는지 봅니다(`freeVoices`).
- **받아 오는 음원**: 받기 전과 받은 뒤의 음색이 연주 도중에 바뀌지 않는가. 받기에 실패하면 다시 받는가.
- **아이폰·아이패드**: 첫 소리는 사용자의 탭 안에서 켜야 합니다. `isAudioUnlocked()`가 실제로 참이 되는지 봅니다. 무음 스위치를 켠 상태도 확인합니다.
- **보안 정책**: `data:`나 `blob:` 주소의 오디오·그림은 `default-src 'self'`에 막힐 수 있습니다. 같은 출처의 파일을 쓰거나 정책을 함께 고칩니다.
- **타이밍**은 가짜 시계로 한 자동 검사와 브라우저에서 잰 값을 구분해 적습니다.

## 4. 실행 화면·시작 흐름을 바꿀 때

`Sandbox.jsx`, `usePyodide.js`, `pyodide-singleton.js`입니다.

- **엔진을 받는 동안** 사용자가 시작을 누르면 어떻게 되는가. 빈 화면에 남지 않고 준비 상태가 보이는가.
- 편집 화면, 전체 화면 실행(`?view=run`), 임베드, 갤러리, 트레이닝이 같은 엔진을 따로 감쌉니다. 한 곳만 고치지 않았는지 봅니다.
- 터치 기기 전용 분기(`isTouchPlaybackEnvironment`)를 데스크톱에서만 확인하지 않았는가.

## 5. 예제·수업 자료를 추가할 때

- **편집기에서 실제로 실행**해 봅니다. 문서·미션·튜토리얼의 코드는 테스트가 실행하지만 `examples.js`의 코드는 종류에 따라 다릅니다.
- **느린 기기**: 프레임마다 갱신하는 물체 수, 반투명 점의 수를 셉니다. 실기기에서 재 보지 못했으면 PR에 그렇게 적습니다.
- **좁은 화면**: 위젯이 장면을 가리지 않는가.
- **내려받은 HTML과 갤러리**에서도 같은 모습인가. 아니면 예제 설명에 적습니다.
- **주석**: 처음 보는 교사가 막힐 줄(긴 한 줄, 기호 이름 변수, 파이썬 고급 문법)에 한글 주석을 답니다.
- **다른 사람의 작품을 참고**했으면 출처를 적고, 그림을 그대로 옮겨 싣지 않습니다.

## 6. 그림·소리 파일을 추가할 때

- 파일 옆의 `SOURCE.md`에 **출처, 이용 조건, 만든 방법**(직접 만들었으면 스크립트와 시드)을 적습니다. 적을 수 없으면 넣지 않습니다.
- 저작자 표시가 필요한 자산은 앱 화면이나 문서에서도 찾을 수 있게 합니다.
- 실제로 쓰는 장면에서만 내려받는지, 첫 화면 용량이 늘지 않는지 확인합니다.
- 4KB보다 작은 파일은 번들러가 `data:` 주소로 바꿔 넣습니다. 보안 정책에 걸리면 `client/public/`에 둡니다.

## 7. 올리기 전에

| 무엇 | 어떻게 |
|---|---|
| 자동 검사 | `client`에서 `npm run test:run`, `npm run lint`, `npm run build`. 파이썬을 실제로 돌리는 테스트는 컴퓨터가 바쁘면 시간 초과가 납니다. 그 파일만 따로 돌리거나 PR의 CI로 판정합니다. |
| 운영과 같은 조건 | PR을 올리면 생기는 Vercel 미리보기 주소. 로컬 미리보기 서버에는 보안 정책이 없습니다. |
| 두 판 | 수업용 판(Vercel)과 오픈소스 판(Cloudflare)은 설정이 다릅니다. 한쪽에서만 본 것은 그렇게 적습니다. |
| 기기 | PC, 휴대폰 크기 화면, 가능하면 실제 아이폰·아이패드. 흉내로 확인한 것은 흉내라고 적습니다. |
| 기존 작품 | 기존 예제 두세 개와 텍스처·소리를 쓰는 작품을 다시 실행해 전과 같은지 봅니다. |
| PR 본문 | 확인한 것과 확인하지 못한 것을 나눠 적습니다. |

`main`에 병합하면 운영 두 사이트에 자동 배포됩니다. 병합은 관리자가 승인한 뒤에 합니다.

## 8. 여럿이(사람·AI) 함께 일할 때

- **같은 파일을 동시에 고치지 않습니다.** 맡은 영역을 나누고, 남의 영역에서 찾은 문제는 PR에 의견으로 남깁니다.
- 다른 PR 위에 쌓은 PR은 CI의 일부만 돕니다. `main`을 향하게 된 뒤 전체 CI를 다시 확인합니다.
- 쌓인 PR의 아래쪽을 스쿼시로 병합하면 위쪽 PR에 충돌이 생기기 쉽습니다. 아래쪽은 병합 커밋으로 넣습니다.
- 현재 상태와 남은 일은 `docs/LIGHT_SOUND_HANDOFF_2026-11-20.md`처럼 날짜가 붙은 인수인계 문서에 적습니다.
